# 2026-09-21

## Session 5 — Reels: TikTok-style sizing, real seeded videos, playback fixes

Request: make the Reels screen work like TikTok (portrait fills the screen, big/landscape
videos shown at "post size" uncropped), swipe smoothly between videos, seed real videos and
load them into the DB, and stop videos showing black.

### Root cause of "all reels are black"
Two independent causes, both had to be fixed:

1. **Dead video URLs.** The seeded reels pointed at
   `https://commondatastorage.googleapis.com/gtv-videos-bucket/sample/*.mp4`, which now
   returns **HTTP 403** — from the PC *and* the device. The old `VideoView` implementation
   swallowed this in `setOnErrorListener` (returned `true`), so it rendered black with no
   error. ExoPlayer surfaced it immediately as
   `HttpDataSource$InvalidResponseCodeException: Response code: 403`.
   Fix: serve media from the backend itself (`/uploads/...`), which `resolveMediaUrl()`
   already rewrites to whatever host the app is talking to.

2. **Decoder exhaustion.** `AdapterReel` created a player per bound page and only *paused*
   off-screen ones, so every visited reel kept its video **and audio** decoders allocated.
   On this device that produced
   `MediaCodecDecoderException: Decoder failed: c2.android.aac.decoder` → `onPlayerError`
   → poster shown forever. Fix: `pausePlayback()` now **releases** the player outright, and
   only the active page is ever given a player.

### Changes

**`updates/app/src/main/java/com/app/myfriend/adapter/AdapterReel.java`** — rewritten video path
- `VideoView` → `androidx.media3.ui.PlayerView` + `ExoPlayer` (media3 1.4.1).
- Poster `ImageView` (`R.id.thumb`) drawn **above** the player, hidden on
  `onRenderedFirstFrame()`. A reel can no longer be a black rectangle.
- **TikTok sizing** in `onVideoSizeChanged()`: `ratio < 1` (portrait) →
  `RESIZE_MODE_ZOOM` (fills screen); otherwise → `RESIZE_MODE_FIT` (post size, uncropped).
  The poster's `scaleType` is switched to match so the hand-off does not jump.
- Progress bar driven by real `STATE_BUFFERING` instead of the old fixed 1.5 s timer.
- `onPlayerError` logs via `Log.e(TAG="AdapterReel")` (Timber was never planted, so the old
  `Timber.e` was silently discarded) and retries **once with audio muted** — this device's
  AAC decoder is the first thing to fail under load.
- `releasePlayer()` calls `player.release()` only (calling `stop()` then `release()` threw
  `IllegalStateException: Reset failed` in `MediaCodec.native_stop`).
- `setActivePosition()` retries via `attachedRecyclerView.post(...)`: `onPageSelected` can
  fire before the incoming page's ViewHolder exists, which left reels stuck on their poster.

**`updates/app/src/main/java/com/app/myfriend/reel/ReelActivity.java`**
- Page-change callbacks drive `setActivePosition`; `onPause` pauses, `onResume` resumes.
- `setOffscreenPageLimit(1)` so the next poster is pre-built for smooth swiping.

**`updates/app/src/main/java/com/app/myfriend/MainActivity.java`**
- Launches `ReelActivity` when `savedInstanceState == null`, so the app **opens on Reels**;
  the home feed is committed underneath, so Back returns to it.

**`updates/app/src/main/java/com/app/myfriend/model/ModelReel.java`**
- Added `thumb` field + getter/setter; `ApiClient.parseReels` now maps `thumbnailUrl`.

**`updates/app/src/main/res/layout/reel_list.xml`**
- `PlayerView` + poster `ImageView`; default `resize_mode="fit"`.
- New drawable `bg_reel_placeholder.xml` (#141414 — deliberately not pure black).

**`updates/app/build.gradle.kts`** — added `androidx.media3:media3-exoplayer:1.4.1`
and `media3-ui:1.4.1`.

### Backend / data
- `backend/scripts/probe-video.js` — reads MP4 dimensions from the `tkhd` box (no ffprobe
  available on this machine).
- `backend/scripts/lib/mongo.js` — shared bootstrap. **Node's c-ares resolver cannot resolve
  the Atlas SRV record on this machine** (`querySrv ECONNREFUSED`) even though `nslookup`
  works, so it derives the non-SRV shard list from `MONGODB_URI`:
  `cluster0-shard-00-00/-01/-02.7khaz.mongodb.net:27017`.
- `backend/scripts/fix-reel-videos.js`, `backend/scripts/seed-reels.js` — repoint/seed reels.
- Videos now in `backend/uploads/`: `reel-portrait-1080x1920.mp4` (**720x1280** portrait),
  `reel-square-1080x1080.mp4` (**720x720**), `reel-landscape-640x360.mp4` (**640x360**),
  plus the existing user upload (**848x478**). All served with `Accept-Ranges: bytes`.
- DB now has **4 reels** covering portrait, square and landscape.

### Verified on the device (Galaxy A10s, SM-A107F)
- App opens on Reels; all four pages play (frames advancing), **0 playback failures**,
  no 403 / codec errors.
- `AdapterReel` sizing log confirms: `848x478 -> post size`, `640x360 -> post size`,
  `720x1280 -> full screen (zoom)`, `720x720 -> post size`.
- Screenshots confirm the portrait reel fills the screen and the landscape reel is
  letterboxed with the full frame visible.

### Device notes (important for future testing)
- The device has **1.8 GB RAM and was running at load average ~21**, and `system_server`
  crashed once mid-test (`DropBoxManagerService: tag=system_server_crash`), showing the
  Samsung boot logo while kernel uptime kept counting. Treat the device as fragile: space
  out launches, avoid rapid force-stop/launch loops.
- A near-identical screenshot pair (tiny byte delta) usually means only the **status-bar
  clock** changed — i.e. the content is static, not playing. Compare frame-to-frame deltas,
  not just `cmp`.
