## Android app (`updates/`) — aligned to the real backend API

**Problem:** the Android app showed hardcoded placeholder data (picsum.photos images,
fake users `shivanshu`/`priyanka`/`spacester`) instead of the real backend content the
Next.js frontend (`Frontend/`) renders. Chat was completely dead because it read from a
stub Firebase shim (`data/ApiDatabase.java` + `DatabaseStorage.java`) whose store was
seeded with fake data and never hit the network.

**Root causes found**
1. `ApiClient.login/register` read the user id from `_id`, but the backend serialises users
   through `utils/toPublicUser.js`, which exposes it as `id`. The app therefore stored the
   *email* as the UID, breaking every authenticated request.
2. `getFeedPosts` called `GET /posts` (raw Mongoose docs) instead of `GET /posts/feed`
   (the serialized payload the frontend consumes), and fell back to `getSamplePosts()`
   whenever the response was empty.
3. Every data method had a `getSample*()` fallback that masked failures.
4. No chat API existed at all — `ChatFragment` listed "discover users" as if they were
   conversations, and `ChatActivity` read/wrote to the dead shim.
5. Media URLs from the backend are `http://localhost:4000/uploads/...` or server-relative
   (`/images/...`), neither of which resolves from an Android device.

## Post interactions wired to the backend via `data/ApiBridge.java` (new)

**Problem:** the post *counts* were blank and every like / comment / save / view / report /
delete still wrote to the dead shim. `adapter/AdapterPost.java` alone has ~80 shim call
sites (`Likes/{pid}`, `Reaction/{pid}/{uid}`, `Posts/{pid}/Comments`, `Views/{pid}`,
`Saves/{uid}/{pid}`, `postExtra/{pid}`, `Follow/...`), and `CommentActivity`,
`LikedActivity`, `ReelLikedActivity`, `AdapterComment` use the same shapes.

**Approach — one central bridge instead of ~80 edits.** `data/ApiBridge.java` (new) maps the
legacy shim paths onto the REST backend:
- **Cache** — `cachePost(JSONObject)` stores the raw serialised post; `ApiClient.parseFeedPosts`
  and `postFromResponse` both call it, so the cache always mirrors `/posts/feed`,
  `/posts/saved` and every interaction response.
- **Reads** — `ApiBridge.snapshot(DatabaseReference)` builds a `DataSnapshot` from the cache
  for `Posts`, `Likes`, `Reaction`, `Views`, `Saves`, `postExtra`, `Users`; anything else
  returns `null` so the caller falls back to `DatabaseStorage` (Ads / Live / balance /
  drafts stay local). Ordering/filtering (`orderByChild().equalTo()`) is still handled by
  the existing `Query.applyFilter`, so `Reaction/{pid}` is returned as
  `{userId: {type: ...}}` and Firebase-style queries keep working.
- **Writes** — `ApiBridge.handleWrite(path, value, isRemove)` forwards to
  `reactToPost` / `addPostComment` / `toggleSavedPost` / `deletePost`, and swallows
  `ReportPost` (no endpoint). `Views` bumps the cached count locally.
- **Dedupe rule (important):** the adapter writes **both** `Reaction/{pid}/{uid}` and
  `Likes/{pid}/{uid}` on every like/unlike. Only `Reaction/...` drives the network call;
  `Likes/...` is cache/notify only. Otherwise each tap would toggle twice and cancel out.
  The unlike path passes the *current* reaction type (read from the cache) so the backend
  toggles it off.
- **Live refresh** — the shim's `notifyListeners` never crossed instances, so the UI could
  not update after a write. `ApiBridge` keeps a path → refresher registry that `Query`
  populates; `notifyPostChanged(postId)` re-runs every listener whose path is under a
  post-related root and mentions that post id. Optimistic cache updates (`optimisticReaction`,
  `optimisticSave`) make the tap feel instant before the response lands.

**Files touched:** `data/ApiBridge.java` (new), `data/Query.java` (bridge-first reads +
refresher registry + `baseSnapshot()`), `data/DatabaseReference.java` (setValue/removeValue
try the bridge first), `data/DataSnapshot.java` (optional `countOverride` so `Views/{pid}`
can report a real count without materialising N entries), `api/ApiClient.java`
(`cachePost` hooks + `getCachedUsersMap()` / `getCachedUserMap()` for the `Users` path).

**Verified:** `./gradlew assembleDebug` → BUILD SUCCESSFUL. Every endpoint the bridge calls
was exercised against the live `extremis` database: react `love` → `viewerReaction=love`;
react `love` again → toggled off (this is the behaviour the dedupe rule depends on);
`like` → `likedByViewer=true`; comment → `commentCount` +1 and message stored;
save → `savedByViewer=true` and the post appears in `/posts/saved`. Test data was removed
afterwards (77 pre-existing comments verified intact).

## Follow / unfollow also bridged

`profile/UserProfileActivity.java` writes **both** `Follow/{me}/Following/{him}` and
`Follow/{him}/Followers/{me}` on every follow/unfollow, and `isFollowing()` reads
`Follow/{me}/Following/{him}`. Both directions are now handled by the same dedupe rule:
- `Follow/{currentUid}/Following/{target}` is the driver → `ApiClient.toggleFollowUser(target, following)`.
- `Follow/{target}/Followers/{currentUid}` is cache/notify only (otherwise it would fire a second call).

`ApiBridge` keeps a session-local `followRelations` map (`"viewer|target"`) so the legacy
`Follow/{uid}/Following` / `Followers` reads are answered from what has been learned; the
backend only reveals follow state per profile request, not as a list. `POST /profile/:userId/follow`
accepts `{following: boolean}` and is idempotent (verified live: follow → `isFollowing:true`,
unfollow → `isFollowing:false`).

**Note:** `UserProfileActivity` does not use `ApiClient` at all — it reads profile data from
the shim, so a *other user's* profile still renders empty. That screen needs a real rewrite
(separate task); the follow action itself now persists correctly.

- **Do not blanket-replace `drawable/btn_round`** — 99 uses, including chat bubbles. Only the

# Session 4 — "device still shows no data" (physical device could not reach the backend)

## Symptom
Backend running (`npm start` → "Auth API running on http://localhost:4000"), app installed on a
**physical** phone over USB, home feed shows the composer but "Nothing Found" / no posts.

## Root cause (two separate bugs)

**1. Windows Firewall was dropping inbound TCP 4000.**
- `netstat` showed the backend correctly listening on `0.0.0.0:4000` **and** `[::]:4000`, and
  `curl http://192.168.0.101:4000/...` from the PC returned 200.
- **But that local test is misleading**: traffic from the PC to its *own* LAN IP does not traverse
  the inbound firewall rule, so a 200 proves nothing about LAN reachability.
- The real test is from the device: `adb shell ping` → 0% loss, but
  `adb shell 'printf "GET ... HTTP/1.0\r\n\r\n" | nc 192.168.0.101 4000'` → **connection timed out**,
  and `netsh advfirewall firewall show rule name=all` had **no rule** for 4000.
- Fix: `netsh advfirewall firewall add rule name="Extremis Backend 4000" dir=in action=allow protocol=TCP localport=4000` (needs admin).

**2. The app's host discovery could not find the PC quickly (or at all).**
- `ApiClient.BASE_URL` defaulted to `http://10.0.2.2:4000/api` (the **emulator** alias) and that
  default was inserted as candidate #1 *every launch*, because `BASE_URL` is a plain static that
  resets on process start.
- On a real device `10.0.2.2` is unroutable, so the socket sits in **SYN_SENT** until the connect
  timeout fires — `netstat` on the device showed
  `::ffff:192.168.0.131:54218 -> ::ffff:10.0.2.2:4000 SYN_SENT`. That stalled the whole candidate
  walk (~20 s before the feed appeared).
- Fixes applied:
  - `isEmulator()` gate — only probe `10.0.2.2` on an actual emulator (fingerprint/model/product/hardware).
  - `localhost` / `127.0.0.1` moved **first**: instant success over USB `adb reverse`, and
    instant *refused* on an emulator, so it never costs a timeout.
  - `rememberBaseUrl()` persists the host that actually answered to
    `SharedPreferences("app_user_session").api_base_url`; `restoreBaseUrlOnce()` puts it first on
    the next launch (only when it was genuinely restored — never the hardcoded default).
  - Own-subnet probe octets reordered to `{"101","100","1","2","10","102"}`.

## USB path that works regardless of firewall/Wi-Fi
`adb reverse tcp:4000 tcp:4000` — makes the **device's** localhost:4000 tunnel to the PC over the
cable. The host side connects to 127.0.0.1, so it bypasses inbound firewall rules entirely and
needs no admin rights. Lost on unplug; re-run after reconnecting.

## Bug 3 — `org.json` optString() returns the literal string "null"
The feed rendered `Aarav Sharma - null 😊` and `aarav_sharma_0 . 3 days ago . null`, and
`user_name` was persisted as `ADMMMM null`.
- Cause: `JSONObject.optString(key, fallback)` uses `fallback` **only when the key is absent**.
  When the key is present but holds a JSON null it returns the text `"null"`.
- The adapters *did* guard with `!= null && !isEmpty()` — the guard passed because the value was
  the 4-character string `"null"`.
- Fix: added `ApiClient.safeString(obj, key[, fallback])` which treats `isNull(key)` **and** a
  literal `"null"` as the fallback, then mechanically replaced **245** call sites
  (165 in `ApiClient.java`, 80 in `ApiBridge.java` — the only two files using optString).
- **Trap:** the regex also rewrote the helper's own body into a self-call (infinite recursion).
  Always re-read the newly added helper *after* a project-wide regex sweep.

## Diagnosis toolkit that actually worked
- `adb exec-out screencap -p > out.png` then read the image — visual confirmation without an emulator.
- `adb shell run-as com.app.myfriend cat shared_prefs/app_user_session.xml` — reads the app's own
  prefs on a debuggable build; this is how the persisted host and the `"ADMMMM null"` name were found.
- `adb shell netstat -an | grep 4000` — shows SYN_SENT vs TIME_WAIT, which distinguishes
  "unroutable host" from "request completed".
- `adb` on Windows needs **Windows paths** (`C:/...`), not MSYS `/c/...` paths.
- `adb` lives at `%LOCALAPPDATA%\Android\Sdk\platform-tools\adb.exe`.

## Correction to an earlier claim
Session 2/3 notes said "live" had no backend endpoint. **That was wrong** — the backend mounts
`/api/live-stream` (`app.js:165`) with `listStreams` / `getActiveStream` / `startStream` / chat /
end, and it currently returns a real stream ("Welcome to Socimo Live Room", status live,
viewerCount 2). The frontend has `app/live-stream`. So the home feed's live row **is** a genuine
unwired gap (the app shows shim placeholders with no thumbnails), not a missing backend feature.
